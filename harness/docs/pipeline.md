# Zone Kit pipeline: plugin → cook → install → release

Verified with ImmersiveDialogue 2.0.0-2.1.1 and ImmersiveCampfires (2026-09-13 → 09-29).

## 1. The plugin
- A mod is a Zone Kit "plain mod" plugin at `<kit>\Stalker2\Mods\<Mod>\` (`<Mod>.uplugin`, `Content\`,
  `Resources\`). **The kit folder is the editor's source of truth**; the repo keeps a mirror in `zonekit/<Mod>/`
  (`mirror_from_kit.ps1` after every save the tester reports; `deploy_to_kit.ps1` for a fresh machine or rollback).
- Create with `<kit>\CreatePlainMod.bat <Mod>` (= `RunUAT GSCCreatePlainMod -ModName=<Mod>`; `new_mod.ps1` does it),
  then give the descriptor `Category "Game Features"`, `Mod: true`, `ExplicitlyLoaded: true`,
  `BuiltInInitialFeatureState "Registered"`, `CanContainContent: true`.
- **GameFeatureData**: the editor discovers a new plugin only at startup, and even then it stays unmounted ("Found
  Mod GameFeature ... without a UGameFeatureData asset ... will not load in Mod Editor"), in the editor and in the
  commandlet. The ModKit creates `/<Mod>/<Mod>` (actions AddToContentPack, AddConfigsPath
  `Content/GameLite/ModGameData/<Mod>/`, AddWorldPartitionContent) and mounts the plugin **when the tester picks
  the mod in the editor's toolbar mod selector**. Do not duplicate another mod's GameFeatureData (its actions carry
  that mod's names and are not Python-editable; the editor also refuses to delete a GFD while running; delete the
  file on disk with the editor closed).
- The toolbar selector also decides which mod "Checkout selected content to mod plugin folder" copies into.

## 2. Overrides vs new content
- **Override** a game asset: Content Browser → right-click → *Checkout selected content to mod plugin folder*. It is
  copied to `Mods\<Mod>\Content\<same relative path>` and ships in `<Mod>Stalker2-Windows-OverrideContent.*`
  (mounted at "/"), replacing the original at runtime. Per asset, the last-mounted pak wins outright: no merging.
- **New content** lives under `/<Mod>/...` (e.g. `/<Mod>/Runtime/BP_<Short>Subsystem`) and ships in
  `<Mod>Stalker2-Windows-NewContent.*`. Unique paths, so no mount-order fight; keep the kit's file name for it.
- Blueprint actor overrides get `Autogenerated_*_ActorReplacementData.uasset` (ReplacementMap game class → mod
  class, applied by `ModActorReplacementSubsystem` at spawn). A plain path override works without it; delete it
  from Content unless an actor override needs it, or it is cooked in.

## 3. Classifier lists
`<kit>\Stalker2\SavedMods\PackageClassifier\<Mod>\OverridePackages.txt` / `NewPackages.txt`, one package path per
line (`/<Mod>/Runtime/BP_X`, `/<Mod>/_Stalker_2/data/input/InputMappingContexts/IMC_X`). The repo mirror is
`zonekit/tools/classifier/<Mod>/`; `cook_and_install.ps1` seeds the kit copy if missing and mirrors it back after
each cook. The editor's Package Mod edits the kit copy itself.
Every asset in the plugin's `Content` is cooked and shipped, listed or not: one missing from `NewPackages.txt` lands
in the OVERRIDE container (ImmersiveLooting 1.3.2: four dev-only assets made it 614 KB instead of 1 KB). Before a
release, delete dev / unused assets from the kit (the asset registry's referencers show what nothing uses; assets
loaded by a path string or a soft class path have no referencers, so check those by hand) and from both lists.

## 4. Cook rules (each verified by extracting the staged containers and reading imports with `zen_names.py`)
- `GSCCookMod` runs two passes ~2 min apart: `-modcooknewcontent` (NewPackages) and `-modcookoverridecontent
  -CookAgainstFixedBase -IgnoreMissingReferences` (OverridePackages).
- **The cook takes everything in the mod's `Content` folder** regardless of the lists. Keep only files meant to ship.
- **A mod package in neither list is cooked into BOTH containers**: into NewContent under its plugin path and into
  the override container as a game-path override (`Stalker2/Content/<folder>/<Asset>`, shipped in `zzz_<Mod>_N_P`).
  ImmersiveLooting 2026-10-10: 25 unlisted animation assets made the override pak 1 KB -> 308 KB (extracted and
  listed with UnrealPak -Extract). After adding assets to a plugin, add them to NewPackages.txt (the kit copy is what
  the cook reads) and check the override container only holds what it should.
- **A package in both lists is cooked into neither.** (`cook_and_install.ps1` warns.)
- **An override-pass Blueprint keeps references only to packages the base game has** (or overrides of them). A pin
  or variable pointing at a mod-only asset compiles in the editor and is silently nulled in the cook, no log line.
  Data assets are different (an override IMC may import NewContent `IA_*` actions and works).
- **A NewContent Blueprint keeps references to other NewContent assets.** So put logic in NewContent hosts.
- `LoadClassAsset_Blocking` on a `/<Mod>/...` soft path returned null at runtime; runtime string loads of mod
  classes are not a workaround. Loading **game-path** assets by string works (`input.md`).
- **Package Mod** (editor toolbar) is the only thing that generates `Autogenerated_<n>_WorldSubsystemData`
  (needed for a `ModWorldSubsystem`, `runtime-host.md`) and writes it into OverridePackages.txt. The headless cook
  does not generate it but cooks it once it exists. Press Package Mod once per mod after creating the subsystem.
- Every game patch may need a re-cook against an updated kit; overrides of changed assets go stale.
  Game 2.1 (2026-10-30, the kit updated the same day to ProjectVersion 2.1.0): re-cooking unchanged
  ImmersiveDialogue sources (pawn override, IMC, AnimInstancePlayer-based ABPs, ModWorldSubsystem) in the new kit gave
  byte-identical packages (one byte differs in the pawn). So 2.1 did not change the cooked layout of those native
  classes; an old-kit cook of them is not stale by itself. A mod that breaks on a patch then broke on game behaviour or
  on a changed vanilla asset it overrides. The game's own containers are not encrypted: `UnrealPak <game>\...\
  pakchunkN-Windows.utoc -List` / `-Extract <dir> -Filter=*Name*` gives the patched vanilla package to diff with
  `zen_names.py` against the mod's cooked copy; a container whose `.ucas` date predates the patch was not touched.

## 5. Cook + install
`powershell -File harness\tools\cook_and_install.ps1 [-Mod X] [-Suffix N]`: RunUAT `GSCCookMod` with
`-UnrealExe=<kit>\Stalker2\Binaries\Win64\Stalker2ModEditor-Win64-Shipping-Cmd.exe` (required; without it UAT looks
for a stock `UnrealEditor-Cmd.exe`), `-TargetPlatform=Win64 -nocompile -nocompileuat`. 5-6 minutes; the editor may
stay open; wait ~10 s after the tester's save. Output under
`<kit>\Stalker2\SavedMods\Staged\<Mod>\Windows\{OverrideContent,NewContent}\Windows\Stalker2\Mods\<Mod>\Content\Paks\Windows\`.
Then it waits for the game to exit and runs `install_paktest.ps1`.
UAT runs **one instance per machine**: a second cook or `CreatePlainMod` fails at once ("A conflicting instance of
AutomationTool is already running"), e.g. while another mod's session is cooking. The tools wait (`Wait-UatFree`).

**Mount order**: priority = 3 + 100 × (N+1) for a `_N_P` file suffix; plain `_P` = 103; kit names = 3.
| Name | Order | Use |
|---|---|---|
| kit name (`<Mod>Stalker2-Windows-...`) | 3 | NewContent (unique paths) |
| `zzz_<Mod>_20_P.*` | 2103 | release override pak: above the usual `_P` / `_10_P` Nexus mods |
| `zzz_<Mod>_30_P.*` | 3103 | dev test pak: beats the Vortex-installed release copy |
| `_40_P` / `_25_P` | 4103 / 2603 | isolation: beat / lose to another mod that ships `_30_P` |

**The NewContent pak has no dev priority.** With the release also installed (Vortex), both copies of
`<Mod>Stalker2-Windows-NewContent.*` have the same name and order 3, and the game ran the release's Blueprints: the
dev pak's override assets changed, its Blueprint logic did not (Campfires 2026-10-01: two test builds "no change",
the probe showed the old graph's behaviour). Before testing Blueprint changes, have the tester disable the mod in
Vortex; `install_paktest.ps1` warns when a second copy is present. Check the folder is really gone: after removing
and re-installing a mod, Vortex can leave the old deployed folder behind (files no longer hardlinked, absent from
`vortex.deployment*.json`), and disabling the mod then does not remove it. Park such an orphan under
`<game>\Stalker2\_parked_mods\`.

Installed to `<game>\Stalker2\Content\Paks\~mods\zzz_<Mod>_PakTest\`. `Content\Paks\` is scanned **recursively**:
never park disabled paks anywhere under it (`revert_paktest.ps1 -Park` moves them to `<game>\Stalker2\_parked_mods\`).
Check the mount in `%LOCALAPPDATA%\Stalker2\Saved\Logs\Stalker2.log` (mount lines show the order).

## 6. Headless editor scripts
`run_headless.ps1 -Script <file.py> [-Arg K=V,...]` runs
`Stalker2ModEditor-Win64-Shipping-Cmd.exe <uproject> -run=pythonscript -script=<file> -unattended -nosplash -stdout
-NoShaderCompile` (~4.5 min). A headless run mounts neither the plugin nor its assets into the registry; the
`editor/` scripts activate the plugin and `scan_paths_synchronous` first. Close the editor for scripts that move,
rename or save assets (a second instance makes the commandlet exit before the script). `delete_asset` on a
never-saved temp asset crashes the commandlet: leave it unsaved instead.

## 7. Release (only on "cut a release")
1. The tester confirms the full test matrix in game (the mod's PLAN.md; include gamepad and coexistence with our
   other mods).
2. Remove the canary, re-cook, mirror, update README / BUILD / AGENTS "Current state", commit on `main`, tag
   `vX.Y.Z`.
3. `make_release.py X.Y.Z --downloads`: zip with `README.txt` + `zzz_<Mod>_20_P.*` (+ NewContent under its kit
   name; optional plugins in their own folders, the Vortex extension's file chooser appears with > 3 pak-type
   files) into `zonekit/builds/vX.Y.Z/`, copy in Downloads for the Nexus upload.
4. Push, `gh release create vX.Y.Z <zip> --notes-file <notes>`; notes in plain player language (they double as the
   Nexus changelog).
5. `revert_paktest.ps1` (game closed) so the tester plays on the Vortex copy, and switch the mod's UE4SS dev probe off
   (`<game>\Stalker2\Binaries\Win64\ue4ss\Mods\mods.txt`: `<Probe> : 0`). A probe left on kept reading the mod's
   actor every 50 ms after the release and crashed the game inside UE4SS (ImmersiveLooting 1.3.1, twice in 6 min,
   `EXCEPTION_ACCESS_VIOLATION`, call stack starting in UE4SS). Say both were done.

Vortex (STALKER 2 HoC extension, Nexus 958): installs pak mods into `~mods`; disabling a mod in Vortex deletes its
deployed folder; deployed files are hardlinks into Vortex staging (copying over them overwrites staging too). For
UE4SS DLL mods it strips `enabled.txt` and writes `mods.txt` only from its "UE4SS Load Order" tab after the user
touches it. Vortex redeploys can rewrite `mods.txt` and remove hand-installed probe folders: re-check after any
Vortex activity.

### Steam Workshop (optional, the tester's clicks)
The Zone Kit uploads by itself (strings in `Stalker2ModEditor-Win64-Shipping.exe`, `ModKitSteamWorkshopManager`;
`DefaultEngine.ini [SteamWorkshop]` app id 1643320): toolbar button **Steam Workshop Upload** → "Upload mod to Steam
Workshop", choose new item or update an existing one, title, description, visibility (Public / Friends / Private /
Unlisted), thumbnail (< 1 MB). It cooks the mod currently picked in the toolbar mod selector and uploads that, so the
kit must hold exactly the released state (deploy `main` first if it doesn't). Needs Steam running, the game owned in
that Steam account, write access to the kit folder. "Item with current name exists already" = choose update instead.
Testing a Workshop copy and a Nexus/Vortex copy of the same mod at once loads it twice: keep one.
A Workshop upload cooks in the kit and changes the plugin there (ImmersiveLooting, 2026-10-11): the root
`Autogenerated_<n>_WorldSubsystemData` is replaced by a new one with another number (same subsystem class), the kit
classifier lists are rewritten (OverridePackages names the new asset) and a `__ModKitWwiseCookAnchor_<Mod>_<n>__`
asset appears in the plugin root. All harmless; mirror afterwards so the repo matches. Tell the tester to upload only
after the last change for that release is cooked and confirmed, or the Workshop gets an older build.
